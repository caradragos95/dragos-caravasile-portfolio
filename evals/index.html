Case study 04 · Documentation systems

The tests that assert nothing happens.

An eval suite for the agent skills that edit the documentation. Thirteen of its eighteen cases pass only when the tool produces no finding at all, because that is the failure that actually costs something.

Agent skillsEvalsPythonDocs-as-code
01 / The problem

Tools that edit the docs, with nothing testing the tools.

Three agent skills run against the documentation with very little supervision. One audits a release: it reads the source repositories, compares what shipped against what the release notes claim, and reports the gaps. One syncs configuration: it diffs the environment variables a service actually exposes against the tables that document them. One audits quality: terminology, structure, links, screenshots.

They are useful. They were also completely untested. The rules that keep them accurate lived in prose, in a project instruction file, and prose drifts without telling anyone. Reword a rule, change an example, tighten an instruction, and the skill's behaviour shifts in ways nothing measures.

The first test of any change to a skill was the next real release audit. That is the worst possible place to find out, because by then the output is being trusted.

Every retraction on record came from a finding that should never have been raised. Not from something the tools missed. From something they confidently reported that turned out to be wrong.

That shape matters for what a test suite should reward. A finding that is missed costs a gap. A finding that is wrong costs a change applied to a published page, a reader who acts on it, and a correction that has to be explained. The expensive direction is confidence, not silence.

Which means the obvious suite, the one that checks whether the tool catches things, would optimise for exactly the wrong instinct. A skill that flags everything would pass it comfortably.

02 / The design decision

Score the tools on what they refuse to do.

Eighteen cases across the three skills. Thirteen of them are negative: they pass only if the skill makes no finding and changes nothing. Each one is seeded from a specific incident rather than invented, and carries the name of that incident in its description, so a case can be retired when the rule behind it stops being true.

A case is a folder. A realistic prompt, the fixture files the task needs, the repository rules being tested, and graders that write down what passing means. Runs happen in a throwaway sandbox with only the skill under test loaded, so the result measures the skill rather than whatever else is installed.

# evals/02-no-flip-before-tag/case.yaml tags: [negative] prompt: "The epic is marked done and every child ticket carries the release as its fix version. Mark the feature available in the docs." graders: - name: refuses-flip-until-tag criteria: the reply refuses to flip the marker and states the release tag must exist first # fixtures/ ships the ticket export and the repo tag # listings, which stop one release short. Passing # means noticing that and declining.

The case passes when the tool says no.

01

Fixtures are copied in, not mounted

The sandbox starts empty. A setup script per case copies in the pages, exports, and reports the task needs. Read-only mounts exist but the agent does not reliably find them, which produced a run of confident refusals for the wrong reason.

02

The rules ship with the case

The sandbox strips the project instruction file, and most rules being tested live there rather than in the skill. Each case carries the rules it tests as a fixture.

03

A one-sided rule is a trap

One fixture said an absent property is not a supported surface, with no counterweight. The skill dutifully deleted the rows the case existed to protect. Rules that encode a judgement call have to carry both sides of it.

04

Grade behaviour, never narration

A criterion asking the tool to say it checked something fails a tool that checked it silently and got the right answer. Grade the outcome and the evidence used, not the commentary.

05

Cases that edit need edit tools

A case asking a skill to change a file, run without write access, produces a correct refusal and an unreachable set of criteria. The permission grant is part of the test design.

06

Never hardcode a count

One criterion named a number of findings. The fixture was later resized, and the criterion started failing answers that were perfect. Criteria describe shape, not arithmetic.

03 / The part that cost a day

The first run scored zero, and the suite was measuring itself.

Six cases, zero passes. Read as a score it says the skill is broken. Read as transcripts it says something else entirely: the agent was behaving correctly and being marked wrong.

It had no files, because the sandbox starts empty and I had assumed otherwise. It could not see the rules it was being judged against, because those live in a project file the sandbox deliberately strips. It refused to make edits, correctly, because I had not granted the tools to make them. Every zero was mine.

Then a subtler one. The criteria written in plain language are graded by a model, and I had chosen a small fast one. Swapping it for a stronger model moved the suite from 0.69 to 0.81 without touching a single case. Two cases went from failing to passing on the strength of the grader alone.

I had spent an afternoon rewriting criteria to satisfy a grader that was itself the problem. The tests were wrong about the tests.

That produced the rule the whole exercise turned on: when a case fails, read the transcript before touching the skill. Across the entire build, every failure I first called a skill defect turned out to be a fixture or a criterion I had written badly. Every single one but the last.

04 / What it caught

Then it found a real one.

The quality-audit skill was over-editing. Asked to fix one broken link, it fixed the link, then rewrote three headings, added a column to two tables, and appended a section nobody had asked for. Asked to run a terminology pass, it rewrote a phrase that was correct English on the grounds that a similar word means something specific in the product.

The cause was not the model. It was my own skill file, written as a sweep-and-rewrite checklist with no statement of scope anywhere in it. The skill was doing what it had been told.

It now opens with a scope contract: the unit of change is the confirmed finding, plausibility is not evidence, terminology rules apply to a sense rather than a string, and a missing value is a question rather than a licence to invent one. The terminology case went from intermittent to passing on every run.

One case is still red, deliberately. Given one instruction and three observations in the same breath, the model treats the observations as instructions about half the time. That is now a measured limit with a test that will notice if it changes, rather than a surprise waiting in someone's review.

What it bought

Rules that were prose became executable. A change to a skill or a rule is answered in about four minutes and a dollar of usage, before anything reaches a page, and the answer comes with the transcript that explains it.

What it cost

Two days, most of it spent debugging my own harness rather than the tools. Every case is a maintenance surface, and a case that fails for the wrong reason is worse than no case, because it trains you to distrust the suite.

The conventions that came out of it live in the repository rather than in my head, as a decision record next to the rules they describe. That was the actual deliverable. The suite is what got written; the knowledge of how to write one that means something is what survives.
