Case study 01 · Docs-as-code migration

The move that made everything else possible.

Roughly 400 pages of enterprise product documentation, off a wiki and into version control, solo, in about six weeks, while the thing being moved stayed in production.

2024SoloMDXGit
01 / The problem

A wiki cannot be held to a standard.

The documentation lived in a hosted wiki. It was editable, it was online, and it was reasonably well written. What it could not do was be checked.

Nothing could validate a link before a reader found it broken. Nothing could tell you which version of the product a page described. Nothing could run in CI, because there was no CI to run. Every rule about quality was a rule somebody had to remember, and rules that live in memory decay at exactly the rate the team gets busy.

The limitation was not the tool's polish. It was that the content was not an artifact you could compute over. Everything downstream of that was blocked.

That is the actual argument for docs-as-code, and it is narrower than the usual pitch. Not that writers should use git because engineers do. That documentation with real stakes needs automated verification, and automated verification needs the content to be files in a repository.

02 / The constraint

The site could not go dark.

A documentation migration has an unusual property: the thing being moved is in production the entire time. Customers are reading it. Support is linking to it. Sales is citing it. There is no maintenance window for a knowledge base.

So the work had to be additive until the moment it was not. Build the new tree alongside the old, keep the old one authoritative until the new one was demonstrably complete, then cut over once rather than in fragments. Half-migrated documentation is worse than either state, because readers cannot tell which half they are in.

03 / The real work

Moving the files was the easy part.

Format conversion is mostly mechanical and mostly scriptable. The work that actually took the six weeks was deciding what the structure should be, because a migration is the only moment you get to change it for free.

Once content is in the new system and people are linking to it, the structure calcifies. Every decision deferred at migration time becomes a decision that needs a redirect map and a change-management conversation later. So the questions had to be answered up front, while the cost of answering them was still zero.

01

Versioned trees, not a versioned page

Readers need to answer "is this available in my version" without cross-referencing a release note. That means the version boundary belongs in the tree structure, not in prose caveats scattered through the body.

02

Navigation as configuration

A file that declares the site structure means the structure can be validated, diffed, and reviewed. It also means a page missing from navigation is a detectable error rather than an invisible orphan.

03

Single-sourced shared content

Facts that appear on many pages get written once and included, so they can be corrected once. Duplication is how documentation becomes quietly wrong in only some places.

04

Branch previews before merge

Every change gets a URL a reviewer can actually read before it ships. Reviewing documentation as a diff is how formatting errors reach production.

04 / What it cost

The honest trade.

What it bought

Everything after it. Validation, quality gates, release discipline, versioning, previews, and automation all became possible the moment the content was files under version control. None of them were reachable before.

What it cost

A real contribution barrier. Occasional contributors now need git and a build, which is a genuine tax on people who used to click edit. That tax has to be paid down deliberately, with templates, previews, and tooling, or contribution quietly stops.

Two years on, the repository holds roughly 2,900 commits. The migration itself accounts for a small fraction of them. That ratio is the point: the migration was not the achievement, it was the precondition for a documentation surface that could be maintained at all.
