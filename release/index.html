Case study 03 · Release management

Shipped means it is in the tag.

Documentation for a platform with two long-term-support lines, a monthly feature release on SaaS, and a new major version that opened its own tree early. Every page has to answer one question correctly: is this available in my version? The answer comes from git, never from a ticket.

Release managementVersioningGitPython
01 / The problem

Four sources of truth, each wrong in its own way.

The release model has three moving parts. Long-term-support families get their own documentation tree, and self-hosted customers stay on one for months. Monthly feature releases go live on SaaS first and reach self-hosted installs only with the next LTS family. A new major version opened its own tree before its LTS existed, so for a while one change could belong in two trees with two different labels.

The obvious places to ask "did this ship?" all lie, just differently. A ticket's fix version lags, sits empty, or names a future release while the code is already out. Merged to main is not shipped, because reverts happen. An epic can sit in the backlog while every child is done. A feature that spans two repositories is available only where both halves shipped, and they don't always ship together.

Two of the errors on record were early, not late: two features marked available a day before a release was cut, on the strength of an expected sync and a product manager's word. Neither made that release.

A missing availability note costs a reader a question. A wrong one costs a self-hosted team an upgrade plan built around something that isn't there. So the system is built to be slow to say yes.

02 / The design decision

Gate on the tag, then route.

Every change goes through a release gate before it reaches a page. The gate resolves a ticket to its commits, then asks git a yes-or-no question for each shipped release: is this commit an ancestor of the tag that release pinned? The pinned tags come from the component tables in the published deployment guidelines, so the documentation is its own release manifest.

# release-gate.py, the mechanism ticket -> commits git log --grep, then a PR search commit -> releases git merge-base --is-ancestor <sha> <pinned-tag> tags <- the component tables in shipped deployment guidelines # never used as the gate fix version a target label, quoted only for parked items merged to main reverts happen epic status the children carry the truth

Topology, not version math.

The verdict then picks the tree, the marker and the release notes from one routing table. Before adopting the table I backtested it against every labeled change of 2026 up to that point, and every one routed correctly.

01

Shipped in an LTS patch

Documented in that family's tree with a plain "available starting with" callout, plus a line in that patch's release notes and deployment guidelines.

02

Shipped only in a feature release

Documented in the current LTS tree with that release's SaaS badge. The page never names the self-hosted target version, because nobody has committed to it yet.

03

Shipped in both

The plain LTS callout wins. A self-hosted reader has it, so the SaaS-only badge would understate it.

04

Shipped in the new major

Plain in the new tree, and mirrored into the current LTS tree with a SaaS badge until the new family reaches general availability.

05

Not released

Documented nowhere. It goes on a watchlist that a daily routine re-gates, so a deferred item can't live only in someone's memory.

06

Renamed or removed

Never a find-and-replace across a tree that still serves readers of the old name. A rename gets a marked note until the next tree fork; a removal gets stripped only where it shipped.

03 / The check that waits

A test that is supposed to pass, until the day it can't.

Every SaaS badge has an expiry date: the day its features reach self-hosted with the next LTS. On that day every badge has to be flipped or removed, across every page that carries one, and that pass used to run from memory. It had missed themes before.

So a validation check now reads every badge and fails the build if the release it names is not newer than the family of the tree it sits in. Today it passes, deliberately. The next LTS tree is created by copying the current one, and the moment that copy exists, every badge it carries fails at once. Nothing can be forgotten because the build won't let anything through until it's handled.

The best time to write the check for a once-a-year task is the month after you last did it by hand.

The badges themselves had a quieter bug. They started as one shared snippet that took the release number as a property. That renders fine for people. But the documentation platform's AI outputs, its search API, its MCP search and its full-text export for language models, dropped snippet properties, so AI readers got an unfilled placeholder where the version should be. The fix was one static snippet per release, with the wording kept identical across them, and a report to the platform vendor.

A version label that only renders for people is one that every assistant answering from the docs never sees.

04 / Where the rules came from

Every rule is a scar.

The playbook's hard rules are short, and each one records the failure that produced it. A few of them:

A search with no control is not evidence

A search for a feature returned zero files on a branch that held thirty, because git grep uses basic regular expressions, where ? is a literal character. The feature was cut from a set of release notes on that zero, then put back. Now every deciding search uses extended syntax and runs next to a control: a pattern known to be present, at the same ref, with its count written down beside the verdict.

Gate where the feature landed

One check followed a ticket's own pointer to a search form that was genuinely unchanged and concluded the feature had not shipped. It had, as column filters on a table and a new page. The gate now looks at the specific surface a reader would touch: the component, the palette entry, the route, the column.

A verdict is a starting point

The gate's fallback PR search once matched a ticket to an unrelated configuration commit and reported it shipped across six releases. The ticket had no fix at all. It fails the other way too: squash merges drop the ticket key from the commit subject, and in one patch harvest 8 of 21 candidates were invisible to key searches. Anything headed for rendered copy gets its commit opened and read.

Diff the file tree, not the ticket list

For feature releases the highest-yield step turned out to be mechanical: list every file added to the application between the previous release's pin and the new one, then write a verdict for each. In one release that recovered three of five themes the ticket-driven pass had missed.

05 / The release notes

Two kinds of release, two shapes of page.

The notes follow a written style contract with a template and a reference page for each release type. A feature release is a set of feature cards, each ending in a link to the page that documents it, with a mechanical sweep checking that every linked page carries an availability signal. An LTS patch is one flat page: a highlight, upgrade notes with every operator action restated as a bullet, then a full changelog grouped as new, changed, fixed, removed and security.

The patch page is flat on purpose. Customers read patch notes as reference, mid-upgrade. Tabs and collapsed sections hide the upgrade actions, break find-in-page and take away the table of contents, which are the three things that reader needs.

What it bought

"Is this in my version?" has an answer anyone can reproduce from git, with the command that settled it. The once-a-year badge flip is enforced by the build instead of by memory, and AI readers get the same version label people do.

What it cost

Ticket systems and git disagree constantly, and every disagreement is work. The gate is slower than trusting a fix version, the playbook only grows, and the gate itself can be wrong, which is why its own last rule says to read the commit.
