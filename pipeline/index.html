Case study 02 · Documentation systems

The check that runs before the mistake ships.

A documentation quality gate where every rule encodes a bug that already happened, and the check fires while the page is being written rather than after it is published.

01 / The problem

Plausible is the dangerous failure mode.

Documentation rarely fails by being obviously wrong. It fails by being plausible: a config value that looks right, reads right, reviews clean, and does nothing when a reader pastes it into production.

Environment variable names are the canonical example. Spring Boot's relaxed binding does not map a property to an env var the way most people assume. It uppercases, converts dots to underscores, and removes hyphens entirely rather than converting them. So app.rate-limit.enabled becomes APP_RATELIMIT_ENABLED, not APP_RATE_LIMIT_ENABLED.

Both forms look correct in a table. Only one works. Reading the source produces the wrong one, confidently, because the property name in the code contains the hyphen that the binding rule deletes. A reviewer checking the doc against the source will agree with the mistake.

The reader cannot detect this class of error. They will conclude the product is broken, not the documentation. That is what makes it worth engineering against rather than proofreading against.

The same shape recurs everywhere: a component used but never imported renders as literal text; a page missing from the navigation config silently breaks the imports on it; a trailing comma in a config file takes down a build. None of these are writing problems. All of them reach readers through the writing.

Scale is what turns them from annoyances into a category. The surface under management is roughly 800 pages carrying more than 4,000 internal links, across two long-term-support version trees plus release notes. Nobody can hold that in their head, and nobody should be asked to.

02 / The design decision

Move the check into the authoring loop.

The obvious place for these checks is CI. CI is also the wrong place, because by the time CI runs the author has moved on, the context is gone, and the feedback arrives as a chore rather than a correction.

Instead the guard runs as an editor hook, after every single file edit. It reads the edit, applies the rules, and on a violation exits with a status that blocks the change and returns the reason as text the author sees immediately. The mistake is corrected in the same breath it was made, with the reasoning still loaded.

Six rules run on every edit. Each one exists because the failure it describes already reached a page.

01

Config files must parse

Any edited JSON must be valid. Catches the trailing-comma class of bug that had broken the navigation config before.

02

No internal ticket keys in rendered copy

Issue-tracker keys are fine as breadcrumbs inside comments, never in text that renders to the public site.

03

No process narration in prose

How a fact was verified is internal process. It belongs in a comment, not on the published page. Code blocks are exempt, since a command shown as an example is legitimate.

04

Components must be imported

A custom component tag with no matching import renders as broken markup rather than failing loudly. The guard resolves every tag against the imports and the built-in component set.

05

No snippet imports on unlisted pages

Imports do not resolve on pages missing from the navigation config, so a shared snippet on an unlisted page renders broken. Either list the page or inline the content.

06

Internal links must resolve

Every relative link must point to a real page, directory, or configured redirect. Same resolver as the pre-commit check, moved earlier.

03 / The part that makes it survivable

Scope the rules to what the edit introduced.

The first version of a gate like this fails for a predictable reason: it blocks on everything it finds, including rot it did not cause. Fixing a typo on a five-year-old page turns into an argument with the linter about six pre-existing broken links. People route around gates that behave that way, and a gate that gets routed around is worse than no gate, because it produces false confidence.

So the structural checks only evaluate content the edit actually introduced. A surgical edit to a legacy page is never blocked for problems it did not create. Template directories are exempt outright, since templates carry placeholder links and components by design.

A quality gate is a product with users, and the users are writers under deadline. If it is not survivable it will not be used, no matter how correct it is.

The rules that stayed absolute are the ones with no legitimate exception: valid config, no internal keys in public copy. The rules with real exceptions got scoped, allowlisted, or exempted in code rather than enforced by nagging.

04 / What it cost

The honest trade.

What it bought

A whole category of error stopped reaching readers, and stopped needing to be remembered. The rules survive turnover, context switching, and the last hour before a release cut.

What it cost

Every rule is a maintenance surface. A check that fires wrongly trains people to bypass it, so the false-positive budget is close to zero, and each new rule has to earn its place against that.

The general principle is narrower than "automate quality" and more useful: encode a rule only after the failure has happened at least once, and scope it so it can only fire on the thing that failed. Rules written in anticipation tend to be wrong about what actually breaks.

The guard's own history is the evidence for that. It went in with two rules. Six weeks later it had six, and every one of the four added since was written after a specific failure reached a page rather than in anticipation of one. Nothing about the final rule set was obvious at the start.
